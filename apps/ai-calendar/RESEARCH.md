## 一、市场调研

### 1.1 现有AI日历产品分析

经过对市场的全面调研，当前主流AI智能日历产品包括:

| 产品 | 核心能力 | 定位 | 不足 |
|------|----------|------|------|
| **Reclaim.ai** | 自动日程规划、智能时间分配 | 职场人士 | 纯SaaS，无本地化，数据隐私弱 |
| **Clockwise** | 会议优化、时间块管理 | 团队协作 | 依赖Google/Outlook生态 |
| **小智日历(DeepSeek)** | AI写待办周报、AI对话做计划 | 国内用户 | 功能相对基础，AI能力有限 |
| **腾讯日历** | 约时间、跨平台同步 | 企业协作 | 缺乏深度AI能力 |

### 1.2 技术方案调研

**现有方案技术栈分析**:

1. **云端AI方案** (Reclaim.ai, Clockwise)
   - 优点: 计算能力强，可处理复杂逻辑
   - 缺点: 数据必须上云，隐私风险高，订阅制费用高

2. **本地化AI方案** (我们项目的差异化方向)
   - 引用自项目根目录的 `Local-First AI Calendar.md` 设计理念:
   - 使用 EdgeVec (WASM向量数据库) 做本地语义搜索
   - Transformers.js + WebGPU 做本地Embedding
   - 严格遵循"计算下沉到端，数据决不上云"原则

## 二、用户痛点调研

### 2.1 现有日历产品核心痛点

基于搜索结果和用户调研分析，当前用户主要痛点包括:

| 痛点 | 描述 | 严重程度 |
|------|------|----------|
| **手动操作繁琐** | 每次添加日程需要输入大量字段(时间、地点、参与者) | 高 |
| **日程冲突难发现** | 多平台日历不同步，冲突检测滞后 | 高 |
| **时间协调困难** | 跨部门、跨组织多人会议约时间极难 | 高 |
| **缺乏智能建议** | 不能根据用户习惯自动优化日程安排 | 中 |
| **数据隐私担忧** | 个人行程暴露给第三方云服务 | 中 |
| **碎片化记录** | 想法、待办、日程分散在不同应用 | 中 |

### 2.2 差异化痛点(我们将要解决的)

1. **灵光时刻流失**: 突然想到的事情没有快速记录入口，事后忘记
2. **Boss与秘书视角割裂**: 现有日历无法区分"老板只需知道时间"和"秘书需要准备事项"
3. **班表生成低效**: 排班需要手动逐个安排，效率低下

## 三、用户习惯调研

### 3.1 日历使用行为模式

根据调研，用户使用日历的习惯可归纳为:

**场景一: 被动记录型**
- 用户: 会议被邀请后，被动添加到日历
- 行为: 打开日历 → 查看今日安排 → 确认时间冲突
- 频次: 高频，每天多次

**场景二: 主动规划型**
- 用户: 主动创建日程、设定提醒
- 行为: 点击添加 → 填写详细信息 → 设置重复规则
- 频次: 中频，每周数次

**场景三: 快速捕捉型**
- 用户: 突然想到要做什么，需要快速记下来
- 行为: 打开应用 → 寻找输入框 → 打字 → 忘记设置时间
- 频次: 中频，但转化率低(常忘记后续处理)

### 3.2 输入习惯分析

- **文字输入**: 仍然是主要方式，但用户渴望更自然的交互
- **语音输入**: 逐渐普及，尤其在移动场景
- **自然语言**: 用户希望说"下周二下午3点见王总"就能自动创建日程

## 四、Boss日历 vs 秘书日历 - 场景深度分析

### 4.1 核心差异

这是本项目的核心差异化功能。通过调研分析，Boss和秘书对日历的需求存在根本性差异:

| 维度 | Boss(老板)视角 | 秘书(助理)视角 |
|------|----------------|----------------|
| **关注点** | 时间节点+关键结论 | 准备事项+执行细节 |
| **信息粒度** | 粗(会议名+时间) | 细(议程+材料+接送+餐饮) |
| **操作模式** | 查看为主 | 安排+跟进+提醒 |
| **决策需求** | 需要知道冲突 | 需要解决冲突 |
| **隐私需求** | 高(行程需要保密) | 需要授权查看 |

### 4.2 具体场景: 老板出差坐飞机

**场景描述**: Boss需要从北京飞上海参加下午2点的客户会议

#### Boss视角(飞机行程):
```
📅 3月15日 08:00-10:30
✈️ 北京→上海 (CA1234)
   到达后直接前往客户公司
```

**Boss只需要知道**: 
- 几点出发
- 几点到达
- 会议时间

#### 秘书视角(需要提前安排):
```
📅 3月15日
├── 07:00 叫车(公司→首都机场T3)
├── 07:30 出发
├── 08:00 到达机场,协助办理值机
├── 08:30 送Boss通过安检
├── 10:30 到达上海,安排接机
├── 11:30 到达酒店,确认会议室
├── 12:00 午餐安排(如果需要)
├── 13:30 提醒Boss准备出发
├── 14:00 客户会议
└── 17:00 返程安排
```

**秘书需要做的**:
- 提前预订机票/酒店
- 安排接送机车辆
- 准备会议材料
- 预订餐饮
- 预订返程
- 多个时间节点提醒

### 4.3 产品设计思路

**双视图模式**:

1. **Boss View (简洁版)**
   - 只显示关键时间节点
   - 一目了然的今日/本周行程
   - 支持语音快速查询

2. **Assistant View (完整版)**
   - 显示完整任务链
   - 任务可勾选完成
   - 自动生成准备事项清单
   - 关联资源(会议材料、接送车辆等)

3. **智能关联**
   - Boss创建一个"出差"意图
   - AI自动拆解出秘书侧的准备任务清单
   - 秘书可以一键确认/调整

## 五、灵光时刻功能设计调研

### 5.1 功能定位

**灵感捕捉(Inspiration Capture)** - 快速记录突然想到的事情，并智能转化为可执行任务或日程。

### 5.2 竞品分析

| 产品 | 灵光时刻功能 | 特点 |
|------|-------------|------|
| **RemSpark闪记** | 一键记录待办&日程 | 支持长文本、截屏、语音自动整理 |
| **Obsidian + QuickAdd** | 闪念笔记 | 快速捕获，可配合日记 |
| **Apple Notes** | 速记 | 简单快速，但与日历割裂 |
| **Goalhacker** | 日历+笔记+待办整合 | 侧边栏快速创建 |

### 5.3 设计方案

**核心特性**:

1. **极速入口**
   - 全局快捷键(桌面端)
   - 悬浮球/小组件(移动端)
   - 首页明显入口

2. **多模态输入**
   - 文字: 快速输入
   - 语音: 语音转文字(集成现有Web Speech API)
   - 截图: OCR识别+提取关键信息

3. **智能分类**
   - AI自动识别内容类型
   - 转化为: 待办/日程/笔记/灵感(仅存储)
   - 自动提取时间信息(如提到"明天3点"自动建日程)

4. **后续处理**
   - 收集箱(类似GTD Inbox)
   - 定时回顾处理
   - 批量转日程

### 5.4 技术实现

- 使用 Transformers.js 做本地NLP意图分类
- 时间实体识别(NER)提取日期/时间
- 存储到本地IndexedDB(通过localforage)

## 六、一键生成班表功能调研

### 6.1 市场需求

排班是很多行业的刚需:
- 餐饮业: 餐厅服务员、厨师排班
- 零售业: 店员排班
- 医疗业: 护士、医生值班
- 制造业: 工人轮班
- 客服: 呼叫中心排班

### 6.2 现有方案

| 方案 | 特点 | 局限 |
|------|------|------|
| **Rotageek** | AI自动排班，30秒生成 | 商业SaaS，付费 |
| **DeepSeek生成VBA** | Excel宏自动化 | 需要Excel专业知识 |
| **WPS+AI** | 零代码协同 | 依赖WPS生态 |
| **纯Excel函数** | 离线可用 | 模板固定，灵活性差 |

### 6.3 设计方案

**核心功能**:

1. **输入参数**
   - 员工名单(可选导入)
   - 班次类型(早/中/晚/自定义)
   - 排班规则(每人每周上班天数、连续休息天数)
   - 日期范围
   - 特殊约束(某日必须有人/不能有人)

2. **AI智能生成**
   - 公平性算法: 尽量均匀分配
   - 偏好学习: 记住员工偏好(某员工prefer周五晚班)
   - 约束满足: 满足所有硬性规则

3. **输出格式**
   - 日历视图展示
   - Excel导出
   - 分享链接(只读)

### 6.4 技术实现

- 前端: 使用启发式算法或约束求解(可选轻量级js求解器如solver.js)
- AI增强: 调用LLM API做自然语言规则解析("尽量让小李每周休周六日")
- 本地存储: 排班数据存IndexedDB

## 八、混合AI模式技术方案

### 8.1 设计原则

根据你的要求，采用**混合模式**: 本地处理简单任务，API处理复杂任务。

### 8.2 混合架构

```
用户输入 → 本地处理判断 → [简单任务] 本地执行 或 [复杂任务] → API处理

本地处理 (边缘计算):
├── 意图分类 (Transformers.js)
├── 时间实体提取 (Regex + 本地NLP)
├── 日程搜索 (EdgeVec)
└── 简单日程创建

API处理 (需要推理能力):
├── 复杂日程拆解 ("老板出差" → 自动生成准备清单)
├── 自然语言理解 ("帮我安排下周和客户的会议")
├── 排班优化算法
└── 多轮对话理解
```

### 8.3 本地处理场景

| 场景 | 处理方式 | 示例 |
|------|----------|------|
| 快速日程创建 | 本地 | "明天3点开会" → 直接解析创建 |
| 日程搜索 | EdgeVec本地 | "找上周的会议记录" → 本地向量搜索 |
| 意图分类 | Transformers.js | 判断用户意图是"创建"还是"查询" |
| 灵光时刻 | 本地 | 快速记录 → 存IndexedDB |

### 8.4 API处理场景

| 场景 | 处理方式 | 示例 |
|------|----------|------|
| 智能任务拆解 | DeepSeek/Claude API | "老板出差北京" → 自动生成10+条准备任务 |
| 自然语言排班 | LLM | "让小李这周上晚班" → 解析规则生成班表 |
| 复杂日程规划 | LLM | "帮我安排紧凑的一天" → 智能时间块分配 |

### 8.5 数据隐私保护

即使使用API，也要遵循最小权限原则:

1. **本地预处理**: 先提取需要的关键信息
2. **只发送必要字段**: 发送给API的只有标题、时间、地点等必要信息
3. **摘要代替全文**: 复杂场景发送AI摘要，而非完整日程
4. **可选本地LLM**: 后续可考虑本地小模型(如Phi-3)处理简单推理

## 十二、思考记录

### 2026-03-12: 初始调研思考

**问**: 为什么现有日历产品无法解决Boss/秘书场景?

**分析**:
1. 现有日历都是单一视角设计
2. 秘书的痛点: 需要做大量准备工作，但日历只显示"会议时间"
3. Boss的痛点: 不关心准备细节，只需要知道时间节点

**解**: 双视图 + 任务链关联

---

**问**: 混合AI模式的优势在哪里?

**分析**:
1. 简单任务(日程搜索、意图分类)本地处理，速度快、免费
2. 复杂任务(任务拆解、复杂规划)API处理，能力强
3. 隐私: 只在API场景发送必要信息，不是全部数据

**解**: 本地优先，API增强

---

**问**: 为什么要用EdgeVec做本地搜索?

**分析**:
1. 日程是短文本，语义搜索很有价值("找上周的会议"比精确搜索更有用)
2. 现有日历产品没有本地向量搜索能力
3. 项目已有EdgeVec包，可以直接复用

**解**: 技术复用，差异化竞争力
